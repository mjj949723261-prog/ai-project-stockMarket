# 股市资讯 App 真实数据接入设计文档

日期：2026-03-09  
范围：`Vue3 H5`、`SwiftUI`、`Flutter` 三端从本地 mock 数据切换到真实数据

## 1. 目标

把当前三端使用的死数据替换成真实数据，并保持三端继续共享同一套产品协议、评分结构和页面信息架构。

本阶段重点不是直接在客户端对接外部数据源，而是建立一层统一的数据聚合与评分后端。

## 2. 免费优先的数据源策略

采用 `AKShare 主源 + Tushare 补充` 的方案。

原因如下：

- `AKShare` 适合作为免费优先的主数据入口，覆盖 A 股行情、历史 K 线、部分基础资料、公告和新闻类能力
- `Tushare Pro` 适合补充结构化财务和部分基础资料
- 纯抓取多个财经站点虽然看起来免费，但维护成本最高，稳定性最差

### 2.1 推荐方案

主数据源：

- `AKShare`

补充数据源：

- `Tushare Pro`

### 2.2 方案取舍

优点：

- 免费可起步
- 覆盖面比单一来源更完整
- 可以逐步扩展，而不是一次性绑定单个供应商

缺点：

- `AKShare` 依赖外部公开站点，底层变更时需要维护
- `Tushare` 免费额度和积分机制会限制部分调用规模

## 3. 架构原则

三端不能分别直接连接 `AKShare` 或 `Tushare`。

正确结构应为：

1. 建立统一后端
2. 后端对接外部数据源
3. 后端生成统一协议结果
4. 三端只调用内部 API

### 3.1 为什么必须统一后端

#### 字段和格式不统一

`AKShare` 和 `Tushare` 的字段命名、时间格式、粒度和返回结构并不一致。

#### 客户端不适合持有凭证

尤其是 `Tushare token`，不应该暴露在 `Vue3`、`SwiftUI` 或 `Flutter` 客户端中。

#### 评分逻辑必须单点维护

“某只股票好不好”不是数据源直接返回的字段，而是你定义的评分规则结果。  
如果评分逻辑散落在三端，结果一定会漂移。

#### 数据源波动需要单点修复

当免费源接口变化时，只改后端适配层即可，不需要三端一起返工。

## 4. 后端 API 设计

第一版建议只做 4 个核心接口，覆盖当前三端现有页面。

### 4.1 `GET /api/stocks/search?q=`

用途：

- 首页搜索股票

数据来源优先：

- `AKShare` 的 A 股股票列表和基础资料

建议返回：

- `code`
- `name`
- `market`
- `industry`

### 4.2 `GET /api/stocks/:code/quote`

用途：

- 获取某只股票的基础行情和最近走势

数据来源优先：

- `AKShare` 的实时行情和日线历史

建议返回：

- `latestPrice`
- `changePercent`
- `volume`
- 近几日价格序列

这些数据主要用于支撑详情页走势和评分历史计算。

### 4.3 `GET /api/stocks/:code/fundamentals`

用途：

- 获取基本面评分输入

数据来源：

- 优先 `Tushare Pro`
- 缺失项再由 `AKShare` 补充

建议返回：

- `revenueGrowth`
- `profitGrowth`
- `roe`
- `debtRatio`
- `cashflowQuality`
- `valuationIndicators`

### 4.4 `GET /api/stocks/:code/analysis`

用途：

- 向三端直接返回聚合后的分析结果

这一层不是外部数据直出，而是你自己的产品核心接口。

建议返回：

- `totalScore`
- 四维分项分
- `verdict`
- `riskWarning`
- `reasons`
- `scoreTrend`
- `scoreHistory`

### 4.5 第一版调用策略

为了降低复杂度，三端第一版应优先依赖：

1. 首页调用 `search`
2. 详情页和自选页主要调用 `analysis`

也就是说，`analysis` 是第一版最核心的真实数据接口。

## 5. 本阶段结论

当前已经确认的设计结论如下：

- 真实数据改造范围是三端同时推进
- 数据源策略采用 `AKShare 主源 + Tushare 补充`
- 三端不直接连外部数据源，必须引入统一后端
- 第一版后端先提供 `search`、`quote`、`fundamentals`、`analysis` 四个接口
- 三端前期重点依赖 `search` 和 `analysis`

## 6. 真实数据评分设计

真实数据接入后，评分设计继续采用 `规则评分为主` 的策略，不直接让模型从原始数据自由打分。

### 6.1 基本面

权重：

- `35`

数据来源：

- `revenueGrowth`
- `profitGrowth`
- `roe`
- `debtRatio`
- `cashflowQuality`
- `valuationIndicators`

评分策略：

- 采用分段规则
- 营收和利润增长稳健时加分
- 负债过高时扣分
- 估值偏高但基本面强时少量扣分

该维度最适合使用确定性规则，因为结构化财务数据相对稳定。

### 6.2 消息面

权重：

- `25`

数据来源：

- 公告
- 新闻
- 财报摘要
- 行业事件

评分策略：

- 先把消息归类成 `利好 / 中性 / 利空`
- 再按影响强度映射成分值变化

第一版采用 `半结构化规则`：

- 可明确归类的消息计入分数
- 无法稳定归类的消息仅展示摘要，暂不计入强分值

### 6.3 技术面

权重：

- `25`

数据来源：

- 最近日线
- 涨跌幅
- 均线关系
- 量价结构
- 短期趋势

评分策略：

- 只做少量关键规则
- 趋势方向
- 短期强弱
- 量能是否配合

第一版不引入过多技术指标，确保分数可解释。

### 6.4 情绪面

权重：

- `15`

该维度是第一版最容易缺数据、也最容易失真的部分。

评分策略：

- 如果有稳定热度数据则正常计分
- 如果缺少可靠热度源，则降级为弱代理信号

可选代理信号：

- 新闻活跃度
- 公告密度
- 近期价格活跃度

也就是说，第一版允许该维度保守上线，而不是为了凑完整度引入高噪音信号。

### 6.5 统一评分流程

第一版评分流程固定为：

1. 拉取外部原始数据
2. 后端清洗成统一字段
3. 规则引擎计算四维分项分
4. 汇总生成总分
5. 生成 `verdict / riskWarning / reasons`

这能保证：

- 分数可追溯
- 三端结果一致
- 后续替换数据源成本更低

## 7. 后端技术方案

第一版后端建议使用 `Python + FastAPI`。

原因：

- `AKShare` 本身是 Python 生态
- `Tushare` 在 Python 中接入最自然
- `FastAPI` 适合聚合型 API 服务，开发效率高

### 7.1 后端模块拆分

建议按以下结构拆分：

#### `providers`

分别封装 `AKShare` 和 `Tushare` 的调用，不让业务层直接依赖第三方字段。

#### `mappers`

负责把第三方返回统一映射成内部模型。

#### `scoring`

负责四维评分和总分计算。

#### `routes`

对外提供：

- `search`
- `quote`
- `fundamentals`
- `analysis`

### 7.2 缓存策略

第一版必须做缓存，否则免费源会很容易被打满或因频繁请求不稳定。

#### `search`

缓存时间较长：

- 数小时到一天

#### `quote`

缓存时间较短：

- 几十秒到几分钟

#### `fundamentals`

缓存时间较长：

- 一天

#### `analysis`

缓存时间中等：

- 几分钟到十几分钟

### 7.3 失败兜底

失败处理建议做两层：

1. 外部源失败时优先返回最近缓存
2. 如果没有缓存，则返回降级结果而不是整页报错

例如：

- 某一维度暂时无法更新
- 当前分析基于最近一次成功同步结果

### 7.4 更新机制

第一版建议同时支持两类更新：

#### 按请求触发

用户查询某只股票时，如果缓存过期，则实时刷新。

#### 后台定时刷新

定时更新：

- 热门股票
- 自选股票
- 最近访问股票

这样既能控制请求成本，也能改善常看股票的体验。

### 7.5 本阶段后端结论

第一版后端不是简单代理第三方接口，而是一个：

`以缓存为中心的数据聚合和评分服务`
